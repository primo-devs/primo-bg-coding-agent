# Primo Fork Guide

This repo is a fork of
[ColeMurray/background-agents](https://github.com/ColeMurray/background-agents). To keep upstream
syncs cheap, every Primo-specific change lives in a separate file or behind a small hook into an
upstream file. This document explains what we changed, where, and how to extend the fork without
growing the drift.

## Philosophy

1. **Minimize diffs against upstream.** Every line modified in an upstream file is a potential
   source of conflicts on the next sync.
2. **New files over modified lines.** If it can live in a new file (overlay, module, our own
   workflow), put it there.
3. **One-line hooks.** When you must touch an upstream file, do it in a single line (import + call)
   that delegates to a file of ours.
4. **Configuration through variables.** If upstream hardcodes something we need to parameterize, add
   a Terraform variable and keep the default equal to upstream's value — that way the change is
   nominal, not semantic.

## Inventory of changes

### Files we own outright

- **`packages/modal-infra/src/images/primo_overlay.py`** — extra installs on the sandbox base image:
  the Core CI Go toolchain, AWS CLI v2, local PostgreSQL backed by `/dev/shm` and tuned like CI, CI
  locale/MIME data, and a `PATH` that includes `/usr/local/go/bin`. Exposes the overlay helpers and
  the Primo sandbox startup command.
- **`packages/slack-bot/src/classifier/primo-classifier-instructions.ts`** — Primo-only Slack
  repository classifier instructions. Defaults unspecified Slack requests to the `core` repository.
- **`.github/workflows/sync-upstream.yml`** — daily workflow that merges `upstream/main` and opens
  an auto-merging PR when there are no conflicts. See [Sync with upstream](#sync-with-upstream).

### Minimal hooks into upstream files

- **`packages/modal-infra/src/images/base.py`** — 2 lines:
  `from .primo_overlay import apply_primo_overlay` and `apply_primo_overlay(base_image)` before the
  final `.add_local_dir`.
- **`packages/modal-infra/src/sandbox/manager.py`** — imports the Primo overlay runtime helpers,
  applies the Postgres layer to pre-built images, and uses `PRIMO_SANDBOX_COMMAND` at the three
  Modal sandbox creation sites so Postgres starts before the supervisor. Sandboxes for
  `primo-devs/core` use Modal's VM runtime with 2 cores and 8192 MiB by default; explicit resource
  settings still override those CPU and memory defaults.
- **`packages/slack-bot/src/classifier/index.ts`** — 2 lines: imports
  `PRIMO_CLASSIFIER_INSTRUCTIONS` and appends it to the Slack classifier prompt.
- **`terraform/environments/production/primo-overrides.tf`** — owns the Primo Slack model variables
  and maps them to named Worker binding overrides.
- **`terraform/environments/production/workers-slack.tf`** — one line passes the Primo override map
  to the Worker module. The upstream `DEFAULT_MODEL` and `CLASSIFICATION_MODEL` binding declarations
  stay unchanged.
- **`terraform/modules/cloudflare-worker/`** — supports optional plain-text binding overrides by
  name so fork-specific values do not have to replace upstream declarations.

### Lockfiles and misc

- `.gitignore`, `package-lock.json`, `terraform/environments/production/.terraform.lock.hcl` — minor
  differences generated by our local development environment.

## How to extend

### Add something to the sandbox (packages, runtimes, CLIs)

Goes into `primo_overlay.py`, **never into `base.py`**.

```python
# packages/modal-infra/src/images/primo_overlay.py

def apply_primo_overlay(image):
    return (
        image.apt_install("postgresql-client", "<new-package>")
        .run_commands(
            # your new install here
        )
        .env({"PATH": "..."})
    )
```

**Cache considerations**:

- `apply_primo_overlay` runs **before** `.add_local_dir(SANDBOX_RUNTIME_DIR)`. That's deliberate:
  the heavy layers (downloads, compiles) must run before the runtime code copy so they don't get
  invalidated every time someone edits the bridge.
- If you add something that changes frequently to the overlay, put it at the **end** of the overlay
  so it doesn't invalidate the layers above it.
- To force a rebuild of the whole image, bump `CACHE_BUSTER` in `base.py` (the overlay inherits it
  via the operation graph). If only the overlay changed, bump `PRIMO_SANDBOX_VERSION` in
  `primo_overlay.py`.

### Parameterize a value that upstream has hardcoded

Standard pattern:

1. Add `variable "foo"` in `terraform/environments/production/primo-overrides.tf`.
2. Add the upstream binding name and `var.foo` to `local.primo_slack_plain_text_binding_overrides`.
3. Leave the upstream binding declaration unchanged. The Worker module applies the override by
   binding name.

Real example: `slack_default_model` overrides `DEFAULT_MODEL` without changing the corresponding
line in `workers-slack.tf`.

### Add a workflow of our own

Drop a new file under `.github/workflows/<name>.yml`. Never modify `ci.yml`, `terraform.yml`, or
`deploy-web.yml` unless strictly unavoidable.

### Modify control-plane / bots / web / etc. code

For small behavior tweaks (constants, defaults), use the Terraform-variable pattern described above.

For bigger changes (custom features, business logic), evaluate **before touching**:

- Can it live in a new file plus a one-line hook in the upstream file?
- Can it be done via external configuration (env vars, secrets) without touching code?
- If neither: touch the upstream file, but keep the diff **as small as possible** and tag it with a
  `# primo: <reason>` comment so it's easy to spot during future syncs.

## Sync with upstream

### Automated

The workflow `.github/workflows/sync-upstream.yml` runs **daily at 09:00 UTC (06:00 ART)**:

1. Fetches `upstream/main`.
2. If there are no new commits → does nothing.
3. Creates `sync/upstream-YYYY-MM-DD` from `main` and merges upstream.
4. **Clean merge** → opens a PR and queues it with `gh pr merge --auto --merge`. When CI passes,
   GitHub merges on its own. After that, the CI/Terraform workflows on `main` deploy automatically.
5. **Conflicts** → commits the markers, opens a **draft** PR, does not enable auto-merge. You
   resolve by hand (see below).

Triggerable manually from Actions → "Sync with upstream" → Run workflow, or via CLI:

```bash
gh workflow run sync-upstream.yml --repo primo-devs/primo-bg-coding-agent
```

### Manual

If you need to sync outside the cron window:

```bash
git checkout main
git pull origin main
git fetch upstream main
git checkout -b sync/upstream-$(date -u +%Y-%m-%d)
git merge upstream/main --no-edit
# resolve conflicts if any
git push -u origin HEAD
gh pr create --base main --title "chore: sync with upstream $(date -u +%Y-%m-%d)"
```

### Resolving common conflicts

When the daily sync opens a draft PR with conflicts, the likely conflict zones are:

- **`packages/modal-infra/src/images/base.py`** — if upstream touched the area where we insert
  `apply_primo_overlay`. Restore the hook (import + wrap) and keep upstream's surrounding changes.
- **`terraform/environments/production/workers-slack.tf`** — if upstream changed the module call
  around the one-line `plain_text_binding_overrides` hook. Preserve upstream's binding declarations
  and reapply only that hook.

After resolving:

```bash
git add <files>
git commit
git push
```

Mark the PR as "Ready for review" in the UI when you're done. CI will run from that point, and you
can merge.

## Sync workflow prerequisites

Documented here so it doesn't get lost:

- **Branch protection** on `main` with the 13 CI checks marked as required (Terraform checks are
  excluded because they have path filters).
- **Secret `SYNC_TOKEN`**: fine-grained PAT with `Contents: write` + `Pull requests: write` on this
  repo. Without it, the PRs the workflow opens don't trigger CI and auto-merge never completes. When
  it expires, regenerate it from https://github.com/settings/personal-access-tokens and replace the
  secret with `gh secret set SYNC_TOKEN`.
- **Auto-merge enabled** at the repo level (Settings → General → Pull Requests → Allow auto-merge).

## Checklist when bringing a Primo-specific change

Before merging a PR with our own changes:

- [ ] Is the change in a new file rather than modifying an upstream one?
- [ ] If it touches an upstream file, is the diff as small as possible (ideally 1-3 lines)?
- [ ] Is the inventory in [Files we own outright](#files-we-own-outright) or
      [Minimal hooks](#minimal-hooks-into-upstream-files) updated?
- [ ] Are there sensible defaults matching upstream where applicable?
